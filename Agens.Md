# Инструкции для агентов

## Назначение проекта

Проект `napopravku-slot-analyzer` — веб-анализатор свободных слотов врачей на `napopravku.ru`.

Целевой сценарий: менеджер открывает опубликованный сайт, вставляет ссылку на страницу клиники, врачей или специальности НаПоправку, запускает анализ и получает:

- врачей, у которых больше 3 свободных слотов на сегодня;
- врачей, у которых больше 3 свободных слотов на завтра;
- прогресс анализа в процентах;
- Excel-выгрузку;
- редактируемое коммерческое предложение с кнопкой копирования.

Коллеги не должны устанавливать Node.js, Codex, GitHub или локальные файлы. Для них продукт должен работать как обычный сайт.

## Текущий стек

- Runtime: Node.js, ESM-модули (`"type": "module"`).
- Сервер: встроенный `node:http` в `server.js`.
- Анализ страниц: Playwright Chromium.
- Фронтенд: обычные HTML/CSS/JS без сборщика.
- Публичная статика: папка `public/`.
- Docker: образ `mcr.microsoft.com/playwright:v1.59.1-noble`.
- Деплой: Render Web Service через Docker.
- Репозиторий: GitHub.

## Основные файлы

- `server.js` — HTTP-сервер, API анализа, очередь задач, запуск Playwright.
- `lib/job-manager.js` — отдельная очередь задач: `jobId`, статусы, прогресс, лимит параллельных анализов, тайм-ауты.
- `lib/browser-options.js` — безопасные настройки запуска Chromium для Render и локального фона.
- `lib/analyzer-timings.js` — управляемые паузы и лимиты ожидания для подгрузки врачей и слотов.
- `lib/url-normalizer.js` — проверка и нормализация ссылок НаПоправку для API.
- `public/index.html` — разметка интерфейса.
- `public/app.js` — логика фронтенда, опрос статуса задачи, Excel, КП.
- `public/style.css` — стили интерфейса.
- `tests/*.test.js` — быстрые проверки очереди, тайм-аутов, настроек Chromium и таймингов анализа.
- `package.json` — зависимости и команды.
- `Dockerfile` — Docker-окружение для Render.
- `render.yaml` — Render Blueprint.
- `README.md` — пользовательское описание проекта.

## Переменные окружения

- `PORT` — порт сервера, по умолчанию `4355`.
- `HOST` — хост сервера. На Render используется `0.0.0.0`.
- `RENDER` — признак запуска на Render.
- `PLAYWRIGHT_HEADLESS` — запуск Chromium без видимого окна. Для Render должно быть `"true"`.
- `MAX_PARALLEL_ANALYSES` — сколько тяжелых анализов можно выполнять параллельно. Целевое значение для платного Render: `5`.
- `ANALYSIS_TIMEOUT_MS` — максимальное время одного анализа. Целевое значение: `900000` миллисекунд, то есть 15 минут.

## Render

Проект рассчитан на Render Docker Web Service.

Для стабильной работы с Playwright нужен не Free/Starter, а минимум инстанс уровня Standard с большим объемом памяти. Бесплатный тариф 512 MB уже показывал нестабильность и перезапуски при анализе тяжелых страниц.

Важно: `render.yaml` может не всегда отражать фактический выбранный тариф в интерфейсе Render. Перед выводом проекта коллегам проверять в Render, что сервис `napopravku-slot-analyzer` запущен на Standard.

## Правила кода

- Не добавлять сборщик фронтенда без необходимости. Сейчас проект специально простой: HTML/CSS/JS.
- Не смешивать результаты разных пользователей. Каждый анализ должен иметь свой `jobId`, прогресс и результат.
- Не хранить состояние анализа только в DOM. Источник статуса — серверная задача.
- При изменении анализа учитывать кнопку `Показать ещё`: она может появляться несколько раз после прокрутки.
- Не делать интерфейс техническим. Сообщения должны быть понятны менеджерам.
- Не показывать пользователю видимый Chrome. Анализ должен идти в фоне.
- Для параллельных анализов использовать общий Chromium и отдельные context/page на задачу, а не запускать отдельный браузер на каждый анализ. Это снижает риск падения Render по памяти.
- Не ломать поддержку ссылок:
  - страницы клиники;
  - `/vrachi/`;
  - страницы специальности `/doctors/.../`.
- Любая ошибка одной карточки врача не должна ронять весь анализ.
- Если часть данных собрана, по возможности возвращать частичный результат.
- Excel должен быть одной таблицей, а не набором листов.
- КП должно оставаться редактируемым на сайте.

## Формат результата

Основной фильтр:

- врач попадает в результат, если у него больше 3 окон сегодня или больше 3 окон завтра.

Для каждого врача сохранять:

- ФИО;
- специализация;
- филиал / клиника;
- адрес;
- окна сегодня;
- окна завтра;
- количество окон сегодня;
- количество окон завтра.

## Excel

Кнопка `Скачать Excel` должна выгружать один файл с одной таблицей.

Колонки:

- `Врач`
- `Специализация`
- `Филиал / клиника`
- `Адрес`
- `Окна на сегодня`
- `Окна на завтра`
- `Количество окон сегодня`
- `Количество окон завтра`

В колонках с окнами времена перечисляются через запятую.

## Коммерческое предложение

После анализа должен появляться редактируемый блок `Коммерческое предложение`.

В нем используется базовый текст:

```text
Здравствуйте!

Я проанализировала расписание врачей вашей клиники и обратила внимание, что у некоторых специалистов на сегодня-завтра остаются свободные окна. Такие слоты особенно важно закрывать оперативно: смена врача уже запланирована, ресурсы клиники задействованы, но при незаполненном расписании часть потенциальной выручки может быть потеряна.

В этой ситуации можно точечно подключить Горящие слоты и Аукцион на НаПоправку. Горящие слоты помогут выделить ближайшие окна для пациентов с помощью специальной скидки и дополнительной подсветки, а Аукцион повысит видимость нужных врачей или услуг в выдаче. Так мы будем продвигать не всех специалистов подряд, а именно тех, кому сейчас нужна дозагрузка.

Это позволит быстрее закрывать свободные окна на ближайшие даты, снизить простой врачей и получить дополнительные записи без массового снижения цен по всей клинике.
```

К тексту можно добавлять автоматически сформированный список врачей и окон. Менеджер должен иметь возможность вручную отредактировать КП и скопировать его кнопкой.

## Прогресс анализа

Интерфейс должен показывать:

- текущий этап;
- текстовое пояснение;
- процент;
- сколько врачей найдено;
- сколько врачей проверено.

Примерные этапы:

- запуск анализа;
- открытие страницы;
- ожидание карточек врачей;
- подгрузка врачей;
- анализ слотов;
- подготовка результата;
- готово.

Проценты могут быть приблизительными, потому что НаПоправку не всегда заранее отдает точное количество карточек.

## Параллельная работа

Менеджеры могут запускать анализы с разных браузеров и компьютеров.

Требования:

- каждый запуск создает отдельную задачу;
- задачи не смешивают прогресс и результаты;
- одновременно должно выполняться до 5 анализов;
- 6-й и следующие анализы должны получать статус `queued`;
- интерфейс должен показывать `Анализ в очереди` и позицию в очереди;
- queued-анализ должен запускаться автоматически, когда один из 5 активных анализов завершится;
- лимит параллельности регулируется `MAX_PARALLEL_ANALYSES`;
- зависшая задача должна завершаться по `ANALYSIS_TIMEOUT_MS`, чтобы не держать очередь бесконечно;
- при росте нагрузки архитектура должна позволять добавить больше ресурсов или вынести анализ в отдельные worker-процессы.

## Самопроверка перед публикацией

1. Проверить синтаксис:

```bash
node --check server.js
node --check public/app.js
```

2. Запустить автотесты:

```bash
npm test
```

Ожидаемо: все тесты проходят.

3. Запустить локально:

```bash
npm start
```

4. Открыть:

```text
http://localhost:4355
```

5. Проверить интерфейс:

- форма принимает ссылку;
- прогресс появляется после запуска;
- результаты отображаются;
- Excel скачивается;
- КП появляется и редактируется;
- кнопка копирования КП работает.

6. Проверить API вручную:

```bash
curl -X POST http://localhost:4355/api/analyze \
  -H "content-type: application/json" \
  --data '{"url":"https://napopravku.ru/kirov/clinics/sovermed/vrachi/#doctors"}'
```

Затем опросить:

```bash
curl http://localhost:4355/api/job/<jobId>
```

6. Проверить минимум такие типы ссылок:

- клиника;
- клиника `/vrachi/`;
- специальность `/doctors/.../`;
- страница с `Показать ещё`;
- страница без подходящих слотов.

7. Проверить параллельность:

- запустить шесть анализов почти одновременно;
- убедиться, что у каждого свой `jobId`;
- убедиться, что первые 5 анализов получают `running`;
- убедиться, что 6-й анализ получает `queued`;
- убедиться, что queued-анализ стартует автоматически после завершения одного активного анализа;
- убедиться, что результаты не смешиваются.

8. После деплоя Render проверить публичный сайт:

```text
https://napopravku-slot-analyzer.onrender.com
```

## Важные ограничения

- НаПоправку может временно ограничивать автоматический анализ. Это внешний фактор.
- Нельзя гарантировать отсутствие ошибок на 100%, но нужно снижать их вероятность через повторы, таймауты, частичные результаты и понятный прогресс.
- Ускорение не должно ломать точность подсчета окон.
- Запуск большого количества Chromium-процессов требует памяти. Следить за тарифом Render и лимитом `MAX_PARALLEL_ANALYSES`.
